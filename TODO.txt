  ### filter_completed_trace rewrite summary (src/parser.rs)
  The previous first-match strategy returned the highest alt_index for nullable rules because
  `queue_front` (LIFO) means last-queued alt lands at deque front and completes first.
  Strategy for user-defined rules: prefer non-self-referential alts, then lower alt_index.
  "Self-referential" (as of 2026-06-06) = first matched NonTerm child can reach the rule name via
  `Parser::rule_reaches` (follows user AND `--` rules): direct (`L:L,M`), operator-desugared
  (`(A,A)+`), or indirect (`B→A→B`). For synthesized rules (`--` prefix): still first-match (empty
  zero-factor alt completes at prediction time, always first in trace).
  See memory/project_filter_completed_trace.md.

  ### Caution: synthesized rule dependency
  If X*/X+/X? equivalence rules are refactored (different alt structure), first-match for
  synthesized rules may break if the empty base case is no longer a zero-factor alt.
  See memory/project_synth_rule_dependency.md for mitigation strategies.

## Performance & Soundness Defects (High Priority)

These were identified in the 2026-06-06 architecture review. #1 (completer position-
index) is DONE. A BROADER re-profile on 2026-06-06 (release `bench --stats` with the
new per-phase wall-time breakdown) overturned the priority order: across REAL grammars
the dominant cost is NOT the Earley parse loop at all — it is TREE EXTRACTION
(`unpack_parse_tree` / `filter_completed_trace`). See the new top item below. The
parse-loop fixes (the O(n^2) item count, clone removal) target only ~2–17% of real
wall-time and drop below the extractor fix in priority. Do the extractor fix BEFORE
the interning item — interning optimizes structures that should first be made the
right shape. Methodology reminder (docs/PROFILING.md): measure, attribute count-vs-
per-op, change one thing, re-measure.

- [ ] De-quadratic the tree extractor (`filter_completed_trace` linear scan) #HIGH  <-- THE DOMINANT REAL-WORLD COST (2026-06-06 broad profile)
  - Evidence (release `bench --stats`, per-phase wall-time): tree extraction
    (`unpack_parse_tree`) is ~98% of the unicode_version grammar build (50.6s of 51.8s;
    the Earley loop is ~1.2s / 2.3%) and ~82% of ixml_self (both build and parse). The
    grammar COMPILE step (`from_parse_tree`) is 0.8ms — negligible. So the single largest
    time sink in the whole suite is the extractor, not the parser core.
  - Mechanism: `filter_completed_trace(name, origin, pos)` LINEAR-SCANS the entire
    `completed_trace` Vec on every call, and is called once per output-tree node; for
    each candidate it may call the recursive `rule_reaches`. Measured on ixml_self (a
    2KB grammar): 9,576 calls × ~48,144-entry trace = 461,026,944 comparisons. Cost is
    O(tree_nodes × |completed_trace| × reach). This is NONE of the parse-loop defects
    (Leo / clones / SPPF all target the loop, ~2–17%).
  - Fix: index `completed_trace` once into `HashMap<(SmolStr,usize,usize), Vec<TraceId>>`
    (or `(NonTermId,usize,usize)` after interning) so each lookup hits a tiny span bucket
    instead of scanning ~48k entries; and memoize/precompute `rule_reaches` (it depends
    only on the grammar, not the parse — a precomputable reachability relation/bitset).
    Expect the heaviest builds to drop from tens of seconds to ~1s. Self-contained, low
    risk; lives in the same extractor machinery g12.c05/SPPF will later touch, so it is
    foundational. Guardrail: full release suite must stay 889/890.
  - Files: src/parser.rs (filter_completed_trace, unpack_parse_tree_internal,
    span_is_ambiguous which has the same scan shape; rule_reaches memo; a completed-
    trace span index built once before extraction)
- [x] Position-index the completer; remove the per-alt continuation fan-out (2026-06-06) #HIGH
  - Problem: there were no per-position Earley sets. `continuations: MultiMap<SmolStr,
    TraceId>` was keyed by nonterminal NAME with no position. On every completion,
    `get_waiting_parent_tasks_by_name` gathered EVERY parent that ever waited on that
    nonterminal anywhere in the whole input, then linearly filtered `pos == origin`.
    Plus a k-fold fan-out: `predict` registered each parent under k separate `name[alt]`
    keys and the getter unioned+duplicated them, saved from incorrectness only by task
    dedup.
  - Done: `continuations` is now `MultiMap<(SmolStr, usize), TraceId>` keyed by
    `(nonterminal, origin_position)` — real Earley-set indexing. `predict` registers
    each parent ONCE at current_pos; getter is a single bucket lookup; the redundant
    `pos == origin` filters in complete() and the nullable path are gone; deleted
    `format_alt_specific_name` and the alt-scanning loop. Renamed getter to
    `waiting_parents_at`.
  - RESULT (profile, NOT what the diagnosis predicted): the fan-out removal is real and
    deterministic — dedup ratio on unicode_version dropped 33% -> 16% (296,836 ->
    117,946 deduped). But tasks created (577,883) and operations (543,186) are UNCHANGED
    and build time moved only ~7% (56.2s -> 52.4s). Synthetic scaling is still
    super-linear: right_recursion ~O(n^2.6), repeat_plus ~O(n^2.5). So the completer
    global-scan was NOT the time-dominant cost. Correctness preserved: 889/890 (only
    g12.c05/SPPF still fails). The structural fix is correct and a prerequisite for
    interning, but the real lever is #2.
  - Files: src/parser.rs (TraceArena.continuations, register_waiting_parent_task,
    waiting_parents_at, complete, predict)
- [ ] Cut the O(n^2) Earley item count (right-recursion blowup) #MED  <-- dominant cost WITHIN the parse loop, but the loop is only ~2-17% of real wall-time (see extractor item above). Real, but smaller than the extractor fix. Leo's optimization is the tool (SPPF will NOT reduce this distinct-item count); also helps X+/X* via the right-recursive desugaring.
  - Evidence (2026-06-06, branch perf/item-set-dedup): the synthetic right_recursion

    So the blowup is NOT "duplicate tasks materialized then deduped" (dedup is zero

- [ ] Stop cloning grammar fragments in the hot loop #MED
  - Problem: `DotNotation::next_unparsed() -> Factor` clones a Factor on every queue pop

  - Solution: have items reference the rule (e.g. &Rule / rule index + dot) instead of
    cloning Factors/TerminalDefns; pass matchers by reference.
  - PARTIAL (2026-06-06): `DotNotation.iteratee` is now `Rc<Rule>`, so `advance_dot`

  - Files: src/parser.rs (DotNotation, next_unparsed, scan, task_advance_cursor,

## Lower Priority - Architecture
- [ ] Intern nonterminals to NonTermId(u32) at grammar-build time (performance) #MED
  - NOTE: do this AFTER the completer-indexing fix above — interning the global
    name-keyed continuations map optimizes a structure that should first be replaced
    with position-indexed Earley sets.
  - Problem: nonterminal names are used as identity keys pervasively (dedup hash in
    task_advance_cursor, continuations map, families map, visited sets, rule_reaches).
    SmolStr makes clones cheap but does NOT help the dominant cost: O(len) SipHash over
    name bytes on every item creation, byte-wise equality, and format!("{}[{}]")
    composite continuation keys rebuilt per lookup.
  - Solution: assign each definition a NonTermId(u32) when the Grammar is built; key all
    maps and Task/MatchRec identity on the id, not the string. Keep the name only for
    display/serialization.
  - Benefits: clone becomes Copy; hashing O(1) on u32 (can drop SipHash for these keys);
    equality a single int compare; smaller Task/MatchRec; continuation key collapses to
    (NonTermId, u32) with no allocation; rule_reaches reachability becomes a precomputable
    bitset.
  - Files: src/grammar.rs (id assignment + name<->id tables), src/parser.rs (Task,
    MatchRec, TraceArena maps, dedup hash, continuations, families, rule_reaches)
